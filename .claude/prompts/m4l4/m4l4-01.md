# M4L4 / Krok 1 — eksploracja z kontraktem (`/10x-research`)

Repo: https://github.com/apache/maven (Java)  
Zmiana: `context/changes/refactor-opportunities/` (z kroku 0)  
Prior: `context/changes/model-builder-flow-analysis/research.md` (+ mapa / inne artefakty, jeśli raport się do nich odwołuje)

## Wymagania konieczne

- Eksploracja kończy się **raportem**, nie decyzją — nie pytaj o wybór / akceptację rankingu.
- Zero zmian w kodzie, zero refaktoru, zero redesignu architektury poza nazwaniem adekwatnego docelowego kształtu per kandydat.
- Nie wyprowadzaj na nowo ustaleń z prioru — buduj na nich; wolno je doprecyzować, gdy kod / git mówią inaczej (evidence / inference / unknown).
- Problemy spoza struktury kodu (np. sama luka testowa, dokumentacja) = **nie kandydat**; zostają wejściem do kosztu / wykonalności.

```text
/10x-research refactor-opportunities Przeczytaj analizę:
context/changes/model-builder-flow-analysis/research.md — zapis długu technicznego
i ryzyk strukturalnych ścieżki budowania modelu POM w apache/maven (Java).
Traktuj jej ustalenia jako zebrane dowody: nie wyprowadzaj ich na nowo, buduj na nich.
Jeśli odwołuje się do innych artefaktów (context/map/repo-map.md, wcześniejszy research),
przeczytaj je również jako priory.

Kontekst stacku (różnica vs lekcja Mattermost/Go PostStore / searchlayer):
- Hot path: core DefaultProjectBuilder → api ModelBuilder (impl…DefaultModelBuilder), nie Save/SQL.
- Twin: compat/…DefaultModelBuilder @Deprecated — connascence M3↔M4 bez krawędzi kompilacji.
- „Persistencja” = reactor / MavenProject / sesja, nie magazyn SQL.
- Testy: unit w module + its/core-it-suite (lustro regresji); CI = reactor Maven, nie Mattermost CI.
- Generowane .mdo / maven-support = tańsze sprzężenie niż ręczne uzgodnienie twinów.
- Typowe problemy z prioru ③ (do wyliczenia i klasyfikacji, nie do ślepego kopiowania):
  hub DefaultModelBuilder (~3450 LOC), drift twin M3↔M4 (m.in. parent relativePath WARNING vs FATAL),
  luki unit (ProjectBuilder, maven3Personality, paired twin), blast radius api/spi/core/compat.

Wypisz każdy problem, który raport odnotowuje, niezależnie od etykiety (dług, ryzyko, hotspot, znalezisko).
Sklasyfikuj każdy: KANDYDAT to problem, którego naprawa zmieniłaby strukturę kodu;
wszystko inne (np. brakujący test, luka w dokumentacji, sam % Jacoco unknown) nie jest kandydatem —
zachowaj to jako wejście do oceny wykonalności i kosztu.
Wypisz listę i klasyfikację kandydatów na początku wyniku, żebym mógł ją zaudytować.

Następnie zbadaj każdego kandydata trzema sub-agentami; wszystkie pracują w trybie eksploracji, bez wprowadzania zmian:

1. Obecny kształt — potwierdź w kodzie, jaki kształt kandydat ma dziś: gdzie żyje logika,
   jak mieszają się odpowiedzialności, jakie abstrakcje lub powiązania już istnieją.
   Cytuj plik:linia. Oznacz każde twierdzenie jako evidence / inference / unknown.
   (Wzorce Java: klasy/interfejsy api vs impl, override metod, call-site’y, twin compat — nie Go interfaces / layer wrappers z lekcji.)

2. Historia i intencjonalność — ustal, DLACZEGO kod ma taki kształt:
   ADR-y i dokumenty projektowe, jeśli istnieją; w przeciwnym razie archeologia gita
   (git log -L, blame, uzasadnienia w commitach i PR-ach).
   Werdykt per kandydat: świadome ograniczenie (decyzja nośna) vs przypadkowa złożoność —
   albo uczciwie oznacz jako unknown, jeżeli ciężko to określić.
   (Przykład z prioru: rozjechane FATAL vs WARNING na relativePath — może być celowe „personality”, nie bug.)

3. Wykonalność migracji — czego wymagałaby inkrementalna, odwracalna ścieżka
   (istniejąca abstrakcja vs nowa abstrakcja; Strangler / Branch by Abstraction / Mikado jako soczewka oceny),
   co wynika z danych o blast radius z raportu, jakie osłony i testy już istnieją wokół
   (unit + ITS; sprawdź konfigurację CI / profile Surefire/Failsafe) i jaki byłby pierwszy krok-prerekwizyt.
   Preferuj „guard, nie przebudowa” tam, gdzie historia wskazuje decyzję nośną.

Twarde granice:
- Żadnych zmian w kodzie. Żadnego refaktoru. Dowody przed interpretacją.
- Nie projektuj docelowej architektury poza nazwaniem adekwatnego docelowego kształtu per kandydat.
- Jeśli prawdziwa naprawa kandydata to przeprojektowanie pojęć domeny POM / modelu (nie struktury kodu) —
  powiedz to i zatrzymaj się: to przedmiot do innej, późniejszej analizy (M4L5).
- Gdzie brakuje danych, napisz unknown — nie wypełniaj luk wiarygodnymi domysłami.

Synteza (po raportach wszystkich trzech subagentów): zapisz research.md w folderze tej zmiany
(context/changes/refactor-opportunities/research.md).
Per kandydat: obecny kształt (z dowodami), werdykt intencjonalności, notatki o wykonalności.

Zamknij sekcją "Refactor opportunities" z 2–3 najmocniejszymi kandydatami w rankingu — dla każdego:
obecny → docelowy kształt, czemu zasługuje na to miejsce (koszt długu vs koszt zmiany),
blast radius, szkic inkrementalnej ścieżki, pierwszy krok-prerekwizyt.
Wypisz też kandydatów rozważonych i odrzuconych, z krótkim podsumowaniem dlaczego.
Oceniaj na podstawie dowodów. NIE proś mnie o wybór, potwierdzenie ani zgodę —
zakończ zapisaniem gotowego raportu.
Ranking to propozycja dla osobnej sesji planowania, która odbędzie się po mojej lekturze.
```
